Why debux?

Modern production images are small, locked-down and often shell-less. That is great for shipping. It is painful when something breaks. debux adds a temporary toolbox next to the container instead of changing the container.

◎

No shell? No problem.

Scratch, distroless and minimal images usually cannot run sh, curl, ps or strace. debux brings those tools from a dedicated debug image.

↔

Debug in place

The debug container shares the target network and process namespaces, then exposes the target filesystem at $DEBUX_TARGET_ROOT.

✦

Nix-powered toolbox

Start with a curated set of tools, then install more with dctl install. Docker stores persist globally; Kubernetes keeps tools when you reuse the same debug container.

Quick start

Install the release binary with one command, then point debux at a Docker container or Kubernetes pod. Docker pulls the debug image automatically; Kubernetes pulls it in-cluster.

curl -fsSL https://raw.githubusercontent.com/clement-tourriere/debux/main/install.sh | sh

debux docker://

# Or browse Docker, Kubernetes and recent sessions
# in the full-screen TUI
debux tui
# Docker picker
debux docker://

# Kubernetes picker, current kube-context namespace
debux k8s://

# Kubernetes picker in another kube context
debux k8s://@eks-preprod-01

# Force a brand-new debug container
debux k8s://prod/api-pod/app --fresh

Full-screen TUI

Use the TUI when you want to find a target visually instead of typing an exact container or pod name. It presents Docker, Kubernetes and History as clear source sections, supports keyboard navigation beyond number shortcuts, and avoids loading every pod at startup.

# Open the full-screen browser
debux tui

# Same command, shorter alias
debux ui

Useful keys

  • / filter the current list
  • tab / shift+tab cycle between the Docker, Kubernetes and History sources
  • 1 / 2 / 3 jump straight to Docker, Kubernetes or History
  • enter drill into source/context/namespace lists or open a selected target
  • b or esc go back in Kubernetes navigation (esc first clears an active filter)
  • s search pods across the selected namespace when the initial pod list is too large
  • t open externally only when DEBUX_TERMINAL is explicitly configured
  • r reload the current view
  • f, c, v, o, p, i toggle fresh, copy mode, volumes, read-only volumes, profile and pull policy
Fast Kubernetes browsing: the TUI first loads kubeconfig contexts only and includes a current context/default namespace shortcut for one-click access. Pods are fetched lazily after you choose a context and namespace, using lightweight metadata. If the namespace is huge, press s from the pod view to search the whole namespace by substring.
No surprise terminal launches: enter always uses the current terminal and returns to the TUI when the shell exits. The optional t shortcut is disabled unless you explicitly set DEBUX_TERMINAL.
Session history: debux records launched sessions in $XDG_STATE_HOME/debux/history.json, or ~/.local/state/debux/history.json when XDG_STATE_HOME is unset, so the TUI can quickly reopen previous debug sessions.

Install

The recommended install path downloads a GitHub Release binary for Linux/macOS on amd64/arm64. Source builds still use mise for Go, hk, pkl and build tooling.

1

One-command install

curl -fsSL https://raw.githubusercontent.com/clement-tourriere/debux/main/install.sh | sh

Installs to ~/.local/bin by default, refuses unverifiable release assets without checksums.txt, and verifies signed checksums when cosign is available.

2

Pin, move, or update

curl -fsSL https://raw.githubusercontent.com/clement-tourriere/debux/main/install.sh | sh -s -- --version v1.2.3
curl -fsSL https://raw.githubusercontent.com/clement-tourriere/debux/main/install.sh | sh -s -- --bin-dir /usr/local/bin

curl -fsSL https://raw.githubusercontent.com/clement-tourriere/debux/main/install.sh | DEBUX_ALLOW_SOURCE_BUILD=1 sh

debux update --check
debux update

debux doctor
debux doctor --strict
debux version --json

debux completion zsh
3

Build from source

git clone https://github.com/clement-tourriere/debux.git
cd debux
mise run install
mise run image-build
Release flow: mise run release:bump then mise run release:push. Pushing a vX.Y.Z tag reachable from main runs the Release workflow, which keyless-signs and publishes the GHCR debug image and creates the GitHub Release with signed checksums and CLI archives. The bump is a no-op when there are no release-eligible conventional commits. Release binaries pin the matching versioned debug image; dev builds use latest.

Mental model

debux does not mutate your target container. It creates a debug companion with tools, then joins what matters.

1. Start a debug toolbox

Docker uses a sidecar container. Kubernetes uses an ephemeral container by default or a copied pod with --copy.

2. Share namespaces

Network and PID namespaces let you inspect localhost services, process trees and attach tools like strace.

3. Mount the target root

The target filesystem is reachable through /proc/1/root and exposed as $DEBUX_TARGET_ROOT.

Inside the shell, run target to jump into the target filesystem. If you run a command the toolbox lacks but the target has, debux runs the target's own binary via chroot into $DEBUX_TARGET_ROOT with the target's original environment — just like docker exec. Otherwise it offers to install the tool with Nix.

Docker debugging

Use debux locally exactly where docker exec stops being useful: distroless images, missing tools, stopped containers, or debugging without rebuilding. Docker Compose services and Podman containers work through the same workflow.

# Start something tiny
docker run -d --name my-nginx nginx:alpine

# Debug by name
debux my-nginx

# Or with an explicit runtime prefix
debux docker://my-nginx

# A Docker Compose service (one replica if scaled)
debux compose://web
debux compose://my-project/web

# A Podman container via its Docker-compatible socket
debux podman://my-app
# Full-screen browser with Docker, Kubernetes and history
debux tui

# Lightweight picker for running containers
debux docker://

# Force a new debug sidecar
debux docker://my-nginx --fresh

# Inject env and Linux capabilities
debux docker://my-nginx --env LOG=debug --cap-add NET_ADMIN

# Do not mount target volumes into the debug container
debux docker://my-nginx --no-volumes

# Or mount target volumes read-only to reduce accidental writes
debux docker://my-nginx --read-only-volumes
Stopped, exited or crash-looping? debux does not error — it copies the target container's filesystem, including its writable layer (logs, crash artifacts, modified config), into a debug container at /target. The original container is never started, and changes outside mounted volumes are discarded on exit. This matches a key docker debug capability.

Persistent Nix store

Docker mode uses image-specific Nix volumes such as debux-nix-store-<image-id>. This keeps installed packages persistent while avoiding stale store volumes after rebuilding the debug image. Treat those volumes as trusted debug-session state; tools installed with dctl can affect later sessions using the same debug image.

Kubernetes debugging

Use ephemeral containers for in-place debugging. If RBAC or policy blocks them, use copy mode to create a temporary duplicate pod; use copy mode carefully for workloads with side effects.

# Current kube-context namespace
debux k8s://
debux k8s://api-pod

# Explicit namespace and container
debux k8s://prod/api-pod/app

# Or pass the namespace as a flag
debux k8s://api-pod/app --namespace prod

# Explicit kube context in the target
debux k8s://@eks-preprod-01/prod/api-pod/app

# Or use --context for complex context names
debux k8s://prod/api-pod/app --context eks-preprod-01

# Not exact? debux proposes matching running pods
debux k8s://prod/webapp-internal-api

# Pull a fresh debug image and force a new container
debux k8s://prod/api-pod/app --fresh --pull-policy=Always
# When pods/ephemeralcontainers RBAC is denied
debux k8s://prod/api-pod/app --copy

# Standalone toolbox pod
debux pod -n prod

# Keep standalone pod after exit
debux pod -n prod --keep

# Debug a node (like kubectl debug node/, with the Nix toolbox)
debux node                      # node picker
debux node worker-1 --profile=sysadmin --keep
Pod name shortcut: if an exact pod name is not found, debux treats it as a substring and opens the searchable picker with matching running pods.
Debug a node: debux node [node-name] schedules a host-namespace toolbox pod (hostPID/hostNetwork/hostIPC), mounts the node root filesystem at /host ($DEBUX_TARGET_ROOT), and tolerates taints so cordoned or NotReady nodes can still be debugged. Node binaries like crictl, journalctl and systemctl run through the chroot fallback with their original host paths.
Kubernetes toolbox persistence: ephemeral containers cannot add new volumes, so debux cannot mount your local Docker toolbox/history into pods. Reuse the same debug container on the same pod to keep installed tools/history, or bake common tools into a custom debug image and pass it with --image. 
FROM ghcr.io/clement-tourriere/debux:latest
ARG NIXPKGS_REF=github:NixOS/nixpkgs/1c3fe55ad329cbcb28471bb30f05c9827f724c76
RUN NIX_CONFIG="experimental-features = nix-command flakes" \
    nix profile add --profile /nix/var/debux-profile \
      "${NIXPKGS_REF}#postgresql" \
      "${NIXPKGS_REF}#redis" \
      "${NIXPKGS_REF}#kubectl"

Shell completion

Generated completions provide live Docker and Kubernetes targets without turning Tab into a cluster-wide scan.

# zsh example
debux completion zsh > ~/.zfunc/_debux

# If replacing an older zsh completion script
rm -f ~/.zcompdump*
exec zsh

What it suggests

  • docker://: running containers.
  • --image and debux image: local Docker images.
  • k8s://: kube contexts, the default namespace, and pods from the selected namespace.
  • k8s://namespace/: pods in that namespace; .../pod/: containers.

Kubernetes pod completion is scoped and cached for speed. Typing 3+ characters also matches substrings, so k8s://inte<Tab> can find webapp-internal-api-....

Inside the shell

The debug shell is zsh with common tools, target-aware helpers, and a small package manager named dctl.

Target shortcuts

echo $DEBUX_TARGET_ROOT
target
ls /target
cat $DEBUX_TARGET_ROOT/etc/hosts

Install missing tools

dctl search postgres
dctl install postgresql
dctl list
dctl remove postgresql

Debug processes and network

ps aux
curl localhost:8080
strace -p 1
tcpdump -i any

Target-binary fallback

Run a command the toolbox does not have but the target does, and debux runs the target's own binary via chroot into $DEBUX_TARGET_ROOT with the target's original environment — like docker exec. Great for app-specific CLIs (a bundled node, php, psql, or a custom entrypoint helper) without installing anything.

Preload tools at startup

Use --tools to auto-install nixpkgs packages before the shell opens. A value can be literal packages or the name of a tool set defined in your config file.

debux my-app --tools py-spy --tools gdb
debux k8s://prod/api --tools python
Some low-level tools need more privileges. In Kubernetes, use --profile=sysadmin for a fully privileged session or --profile=netadmin for network capabilities. --profile=restricted supports shell startup and dctl install with the current debug image, but deep chroot/target-root integration can be limited by Linux permissions. You can also add capabilities ad hoc with --cap-add and inject environment with --env. 
# Run a one-shot command through the debug toolbox; exit code propagates
debux docker://my-app -- curl -fsS localhost/health
debux k8s://prod/api/app -- ps aux

Debug an image directly

Sometimes the target image cannot start at all. debux can copy its filesystem into a debug container and expose it at /target.

# Works with scratch and distroless images too
debux image gcr.io/distroless/static-debian12

# Keep the debug container after exit
debux image my-app:broken --rm=false

Forward ports & copy files

Reach a running target and move files in or out — even for containers started without -p and distroless pods where kubectl cp fails.

# Forward local 8080 to the target's port 80
debux forward my-app 8080:80

# Same local and remote port
debux forward docker://my-app 5432

# A Compose service
debux forward compose://web 8080:3000

# Multiple ports to a pod
debux forward k8s://prod/api-pod 8080:8080 9090:9090
debux forward k8s://api-pod -n prod 8080:8080
# Pull a log file out of a container
debux cp my-app:/var/log/app.log ./app.log

# Pull a heap profile out of a distroless pod
debux cp k8s://prod/api-pod:/app/heap.prof ./

# Push a tool into a pod (destination is a directory)
debux cp ./debug-tool k8s://prod/api-pod:/tmp

# Works with Compose services too
debux cp compose://web:/usr/share/nginx/html ./html
How it works: Docker forward runs a small socat relay on the target's network and publishes the ports on 127.0.0.1, so it works for containers without published ports; Kubernetes uses the pod port-forward API. Kubernetes cp streams through the debux toolbox, so copies work on shell-less images with no tar; Docker cp uses the engine API and also works on stopped containers. Copying into a target treats the destination as a directory.

Scripting & CI

debux is not just an interactive shell. Pass a command after -- to run it non-interactively in the toolbox, and the target's real exit code propagates — so debux drops into scripts and CI pipelines.

# One-shot command, exit code propagates
debux docker://my-app -- curl -fsS localhost/health
debux k8s://prod/api-pod/app -- ps aux

# Use it as a CI gate
debux k8s://prod/api-pod/app -- sh -c 'test -f /app/ready'
# Know before an incident whether debugging is allowed:
# per-profile Kubernetes RBAC preflight
debux doctor k8s://prod/api-pod/app --profile=restricted

# Machine-readable, non-zero exit on any failing check
debux doctor k8s://prod/api-pod/app --json --strict
debux doctor: with no target it checks the debux binary, Docker, and the current Kubernetes context. With a target it focuses on that runtime and, for Kubernetes, evaluates the chosen security profile's required RBAC — a good CI check before granting or relying on debug access.

Configuration

Set defaults once in $XDG_CONFIG_HOME/debux/config.yaml (or the path in $DEBUX_CONFIG). A missing file is fine, and flags always override the config.

image: ghcr.io/clement-tourriere/debux:latest
profile: restricted
pull-policy: IfNotPresent
terminal: wezterm
tools:
  python: [python3, py-spy, gdb]
  net: [socat, mtr, iperf3]

Keys and tool sets

  • image, profile, pull-policy, terminal set defaults for the matching flags.
  • tools maps a set name to a list of nixpkgs packages.
  • --tools python expands a configured set; --tools socat also accepts literal packages.
# Auto-installs python3, py-spy and gdb at session start
debux k8s://prod/api --tools python

Security model

debux is a debugger, not a sandbox. The default Kubernetes profile is intentionally powerful because production debugging often needs process, filesystem, and network visibility.

With the default general profile, a debux session can usually run as root inside the pod, use the pod network namespace, target the selected container's PID namespace, list pod processes, inspect /proc/1/root, mount target volumes directly, and use debugging capabilities such as SYS_PTRACE, SYS_ADMIN, and SYS_CHROOT.

What default debux can expose

  • Pod-local network services via localhost.
  • Pod processes with tools like ps and, when allowed, strace.
  • The target filesystem through $DEBUX_TARGET_ROOT.
  • Mounted secrets, config maps, service-account files, and writable volumes that Linux permissions/capabilities allow.

What it does not grant by itself

  • Root on the Kubernetes node or host filesystem.
  • Access to other pods' filesystems.
  • Kubernetes API permissions beyond your RBAC and the pod's service account.
  • A bypass for PodSecurity, admission webhooks, seccomp, AppArmor, or runtime policy.
ProfilePurposeTypical use
generalDefault. Runs as root and adds useful debugging capabilities like ptrace/chroot.Best UX, highest access inside the pod.
baselineNo explicit security context. Not a non-root guarantee because the image default user is root.Clusters where policy should decide defaults.
restrictedNon-root, drops capabilities, runtime default seccomp. Shell startup and dctl install work with the current debug image, but chroot/target filesystem integration is limited by Linux permissions.Policy-restricted environments.
netadminAdds network capabilities.Network debugging with tools like tcpdump.
sysadminPrivileged container.Last resort for deep kernel/namespace debugging.

--no-volumes only disables direct volume mounts into the debug container, and --read-only-volumes makes those direct mounts read-only to reduce accidental writes. Neither is a security boundary if the debug container can still access the target through /proc/1/root. Kubernetes ephemeral containers also cannot add new volumes, so debux cannot mount your local Docker toolbox/history into arbitrary pods. Reusing the same debug container on the same pod keeps its installed tools; across pods, bake common tools into a custom debug image and pass it with --image.

RBAC implication: granting a user permission to update pods/ephemeralcontainers and create pods/exec is effectively granting the ability to run code inside selected pods. Treat it like production shell access.

# Minimal namespace-scoped RBAC for ephemeral-container debugging
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: debux-debugger
  namespace: prod
rules:
  - apiGroups: [""]
    resources: ["pods"]
    verbs: ["get", "list", "create"]
  - apiGroups: [""]
    resources: ["pods/exec"]
    verbs: ["create"]
  - apiGroups: [""]
    resources: ["pods/ephemeralcontainers"]
    verbs: ["update"]
# Non-root restricted Kubernetes debug shell
debux k8s://prod/api/app \
  --profile=restricted \
  --fresh \
  --pull-policy=Always
# Full privileged debug session
debux k8s://prod/api/app \
  --profile=sysadmin

Store management

Docker installed packages and shell history persist in image-specific Nix volumes. Use the store commands to inspect or clean those Docker stores. Runtime dctl install uses the debug image's pinned nixpkgs revision unless a custom image overrides NIXPKGS_REF.

debux store info

debux store clean

When to clean?

Clean the store if you want to reclaim disk space, reset installed tools, or remove old image-specific Docker Nix volumes after frequent debug image rebuilds. Kubernetes does not use these local Docker volumes.

Troubleshooting

Most failures come from image pull policy, cluster security policy, stale Docker volumes, or trying to debug a container that is not running.

debux talks to the wrong Docker daemon

debux honors the docker CLI's daemon selection: DOCKER_HOST first, then the active docker context (DOCKER_CONTEXT or docker context use), then the default socket — so colima, Docker Desktop and remote daemons work. If debux cannot see a container that docker ps shows, check your context. SSH-based contexts are not supported directly; forward the socket and set DOCKER_HOST.

docker context ls
docker context use colima
# or pin it for one command
DOCKER_HOST=unix:///path/to/docker.sock debux my-app

openat etc/passwd: path escapes from parent

Your cluster runtime rejected NixOS-style absolute symlinks in /etc/passwd or /etc/group. Rebuild and push the latest debug image, then retry with --pull-policy=Always.

mise run image-build
docker push ghcr.io/clement-tourriere/debux:latest
debux k8s://prod/api/app --fresh --pull-policy=Always

/bin/sh: no such file or directory in Docker

This usually means an old Nix store volume was mounted over a rebuilt debug image. Recent debux versions use image-specific volumes. Upgrade and clean old stores if needed.

mise run install
debux store clean
debux docker://my-container --fresh

Ephemeral containers denied

Your RBAC may not allow pods/ephemeralcontainers, or PodSecurity/admission policy blocks the profile. Try copy mode or a less privileged profile.

debux k8s://prod/api/app --copy
# or
debux k8s://prod/api/app --profile=baseline

Image pull failures

Check the debug image name, registry access and imagePullSecrets. For freshly pushed :latest, use --pull-policy=Always.

debux k8s://prod/api/app \
  --image ghcr.io/clement-tourriere/debux:latest \
  --pull-policy=Always

dctl install permission denied in restricted mode

The pod likely pulled an older debug image whose Nix store is root-only. Rebuild and push the current image, then start a fresh restricted session and force a pull.

mise run image-build
docker push ghcr.io/clement-tourriere/debux:latest

debux k8s://prod/api/app \
  --profile=restricted \
  --fresh \
  --pull-policy=Always

FAQ

Short answers to common newcomer questions.

Does debux change my application image?

No. It starts a separate debug container. In Docker it is a sidecar. In Kubernetes it is an ephemeral container or a temporary copied pod.

Can I debug a stopped or crash-looping container?

Yes. debux copies the container's filesystem — including its writable layer — into a debug container at /target without starting the original. Changes outside mounted volumes are discarded on exit.

Why is the debug image large?

It includes Nix and a curated toolbox. Docker reports uncompressed local size. The size buys fast, predictable tools in locked-down containers.

Why do files show as writable?

debux shows the target filesystem as-is through /proc/1/root. If files are 777 there, the target image or volume has those permissions.

Can I use it in restricted clusters?

Yes. Try --profile=restricted for non-root/no-capability sessions, or --profile=baseline for clusters that set defaults via policy. If ephemeral containers are blocked by RBAC, use --copy.
